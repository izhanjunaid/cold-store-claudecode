# 28 — C3: gate safety, papers, the manager queue

C3 was the last part of the fast-dispatch redesign (docs/26). The owner rescoped it on 2026-10-29: most
clients never weigh produce, so the weigh-out check was dropped and weight became optional first
(docs/27). What is left is three jobs that don't depend on each other, so C3 ships as three pull
requests, in the order the owner chose:

1. **Gate safety** (part 1): a loaded truck can't leave on a guessed or zero count, and a booking's
   plate comes from the trucks the gate has logged in.
2. **Papers** (part 2): every PDF button opens its tab first, and the gate's manager box takes a
   dispatch note number.
3. **The manager queue** (part 3): a list of what is waiting for a manager, with the reason.

Only part 1 is built so far. Parts 2 and 3 are designed here and get their build plans when their
turn comes.

> The owner, 2026-10-31: "okay plan c3 that out using relevant skills"

## Part 1 — gate safety

Branch `feat/c3-gate-safety`. Migrations 0043 and 0044.

### D3 — a truck still being loaded can't leave

Before this change the gate released any truck on a count of 0 when no *dispatched* withdrawal matched
its plate. A truck whose withdrawal was booked but not yet checked out therefore left unbilled, with
nothing noticing. `matchByPlate` now takes its lines from the same filter as `openLoads()` (every
booked, weighed, disputed or dispatched line on the plate, not cancelled, not already on a pass; a
line dispatched before Phase 0, with no `finalized_at`, is on no truck). If any of those lines is not
dispatched, the release is refused with `GATE_OUTWARD_NOT_DISPATCHED`:

- even with an override reason, because the fix is at the desk (check out, or cancel), not at the gate;
- before any count is compared, so it does not use up a try;
- on the manager's named-withdrawal path too, which reads `openLoads()` without locking (locking more
  withdrawals after the named one would break the sorted lock order).

An empty truck still leaves on a count of 0.

### D4 — wrong counts are saved, three tries per truck

A guard could retype the count until it matched; nothing recorded the attempts. Now:

- **What counts as a miss:** a release refused for the count, either a mismatch or a count on a truck
  with no load. Each is saved in `gate_count_attempts` (pass, plate, number typed, number expected,
  who, when) and committed even though the release is refused.
- **Per truck, not per pass:** tries are counted per normalized plate since that plate's last CLEARED
  pass, so logging the truck again does not reset them and a release does.
- **The lock:** after `GATE_COUNT_TRIES = 3`, a non-manager is refused with `GATE_OUTWARD_COUNT_LOCKED`
  (403) before any count is compared. A manager is never locked and releases as before, with a count
  or an override reason.
- **Two guards at once:** the count check takes an advisory lock per facility and plate, so two passes
  of one plate cannot both take the last try.
- **What the guard sees:** "Try N of 3, recount", from the error's `details.tries_left`, never a
  figure. `expected_quantity` is a blind key. Managers see the pass's earlier counts.
- **The one-step route** (`POST /v1/gate-passes/outward`, no web caller today) keeps its pass when the
  release is refused, so the attempt has a pass to hang on. It no longer writes `related_outbound_id`
  at creation: a stored link sent a later bare release down the manager-only named path.

### D2, D5 — plates come from the gate

- **Setting** `book_only_trucks_inside` ("Book only trucks inside the gate"), default **off**. While
  off, nothing changes except a warning on the form.
- **When on,** a booking by anyone below manager needs a plate that matches a pass ARRIVED or WEIGHING
  (`OUTBOUND_TRUCK_NOT_INSIDE`). A manager is exempt: this is a fixed seniority rule like backdating,
  not a permission key.
- **The forms:** every withdrawal form and the inbound lot form show the trucks inside as chips. The
  lot form is never strict.
- **30-character plates:** a pass and a withdrawal already took 30; `lots.vehicle_number` is widened
  from 20 (expand-safe) and the schema and masks follow.

### Housekeeping

Two e2e specs asked for passes with `?vehicle=`, but the parameter is `vehicle_number`; the unknown
key was dropped and they read the newest passes instead.

## Part 2 — papers (built; branch `feat/c3-papers`, web only, no migration)

- **D8:** one exported `openPdf(path, what, tab?)` in `apps/web/src/lib/open-pdf.ts`. Only the two
  buttons in `dispatch-pdf.ts` opened their tab before the PDF request; the other 14 opened it after
  the render, which Chrome blocks on a slow box. They all use the helper now (invoices, the withdrawal
  page, the parchi, the placement slip, rack labels, the gate receipt, loans, payroll, the party
  statement), and the two checkout sheets open the dispatch note's or the load slip's tab on the
  click, before the checkout POST, and hand it to the page (`onDone(result, tab)`). Every path that
  does not reach `onDone` closes it, "already checked out" included (filling it would print a second
  slip). `scripts/check-pdf-tabs.mjs` fails CI on a `window.open(` outside the helper.
- **A find made while planning: PDF printing very likely failed on the live box.** A production build
  sets `NEXT_PUBLIC_API_URL=""` (one address behind Caddy; only port 80 is published). `api-client.ts`
  reads it with `??`, so the app worked. All eleven PDF handlers read it with `||`, which turned the
  empty value into `http://localhost:3001`, which nothing serves on a client box. The parchi handler
  had done this since v0.6.2 and swallowed its error, so nothing even said so. The helper reads the base
  with `??`, `fetchPdfBlobUrl()` does the same for the transfer acknowledgment's iframe, and the
  guardrail forbids any other read of the variable (outside `api-client.ts` and the helper).
- **Error wording** now comes from the helper: "Could not open the party statement (500)". The lot
  page used to swallow a failed receipt and the party statement opened an error body as the PDF.
- **D9:** the gate's manager-only "Outbound event ID" box (a UUID) is now "Dispatch note number" with a
  Find button. It looks the number up through `GET /v1/outbound-events?status=DISPATCHED&search=`, and
  accepts only the exact dispatch note (the route matches substrings): a near miss, a note not
  dispatched, or one that already left on another truck is refused in the box, and Clear Outward waits
  while a typed note has not been found. Enter looks it up and releases nothing. The box is no longer
  pre-filled from the pass's stored link. The API is unchanged.
- **D7:** nothing is printed. `.barcode-area` stays text.
- **Known limit:** a withdrawal let out under the old gate rules (a CLEARED pass but a null
  `gate_pass_id`) shows as available in the box; the server refuses it on submit.

## Part 3 — the manager queue (designed, not built)

- **Reason codes.** The eight reasons a munshi is turned away become codes: SOLO_OFF, KATCHI,
  NOT_TODAY, PER_TON_CHARGE, SKIP_CHARGE, NO_STANDING_CREDIT, PAYMENT_MODE, OVER_CREDIT_CEILING. The
  403 gains `details.reason_code` and the previews gain `solo.reason_code`; the prose is unchanged.
- **The list is computed and remembered.** Computed: every ready row (PENDING or WEIGHED) a manager
  must finish — with one-person dispatch off that is every ready row, and with it on, those failing
  the solo rules. Remembered: with it on, the checkout-only refusals (payment mode, credit, a skipped
  charge) are stored on the row after the rollback. A row leaves the list when it is dispatched or
  cancelled.
- **Where managers see it:** a "Waiting for a manager (N)" card on the desk and a count beside
  "Dispatch Desk" in the sidebar, for whoever holds the manager keys. The manager opens the row's
  checkout sheet from the list.
- **"Allow" waits** until a client runs the desk. `:stable` is still v0.6.2, so this part is the
  likeliest to change once someone uses the desk.

## Calls I made (for the owner to check)

- Three tries, one named constant (`GATE_COUNT_TRIES`); the owner was not asked.
- Tries count per truck (plate), not per pass, so logging the truck again is no way round the lock.
- D3 has no override: a manager who needs the truck out checks the booking out or cancels it.
- The part 3 list is computed *and* remembered, because with one-person dispatch off (the default) a
  list of stored refusals would always be empty.

## Known limits

- **A made-up plate.** A guard who logs a made-up plate can still release the real truck as "empty".
  The real truck then stays "inside" with its loads not released, which shows on the desk. Software
  can't see the physical truck.
- **Stale passes stay inside.** A truck that drives off without being released stays "inside"; no
  route closes a pass. With the switch on, a stale pass's plate can still be booked.
- **D3 holds a truck for a forgotten booking of any date.** The desk's queue shows only the last
  three days, so an older booking appears only on the truck card.
- **A truck can come back already locked.** A truck that had three wrong counts and drove off without
  being released is still locked for the guard when it returns, even when empty, until a manager
  releases it.
- **Legacy passes.** A legacy pass still inside with a stored `related_outbound_id` now matches by
  plate. If its withdrawal predates Phase 0 (no `finalized_at`), the truck looks empty, and the
  manager names the withdrawal in the box as before.

## Part 1 as built

Branch `feat/c3-gate-safety`; migrations **0043** (`gate_count_attempts`) and **0044** (`lots.vehicle_number`
to 30 characters), both expand-only, so the previous image keeps running on the migrated database. A
rolled-back image simply never writes the new table, and reads a 30-character plate as it always read
plates.

- **D3:** `matchByPlate` and `openLoads()` share one stage test (`OPEN_LOAD_STAGE_SQL`). The manager's
  named-withdrawal path reads the pass's plate through `openLoads()` unlocked (a second lock after the named
  row would break the sorted lock order).
- **D4:** `gate_count_attempts` (pass, normalized plate, typed, expected, who, when). The saved row commits
  with the refusal through `KeptRefusal` / `withKeptRefusals`. The plate's advisory lock serializes two
  passes of an empty truck; a loaded truck is serialized by its withdrawal rows. `GATE_COUNT_TRIES` (3)
  lives in `@coldchain/shared` so the gate page prints "Try N of 3" from the same number.
- **D2, D5:** the `book_only_trucks_inside` setting (Settings → Dispatch), `OUTBOUND_TRUCK_NOT_INSIDE`, the
  `TrucksInsideChips` component and `useTrucksInside()` (one cache entry with the dispatch desk, read only
  by holders of `outbound.record`).
- **Visible change on the one-step route:** `POST /v1/gate-passes/outward` that is refused for its count now
  leaves its pass inside, with the wrong count saved. It has no web caller today.

### Before promoting (read-only, for the owner)

D3 holds a truck for an open booking of any date, and the desk's queue only lists the last three days.
Cancel old bookings at the desk first. They already reserve stock, so this is worth doing anyway:

```sql
SELECT dispatch_note_number, vehicle_number, status, outbound_date
FROM outbound_events
WHERE status IN ('PENDING', 'WEIGHED', 'DISPUTED')
  AND voided_at IS NULL
  AND gate_pass_id IS NULL
  AND vehicle_number IS NOT NULL
  AND outbound_date < (now() AT TIME ZONE 'Asia/Karachi')::date
ORDER BY outbound_date;
```

### After the whole-branch review

- "Ready to leave" shows a truck the guard has locked out as `COUNT_LOCKED` ("Counts did not match — call a
  manager"), not READY; a manager still sees it as READY because a manager is never locked.
- The guard gets `count_attempts` as null: a manager's or another guard's wrong count sits near the truth.
  Managers get the list; the guard is told only "Try N of 3".
- A typed count is bounded (1,000,000), so a typo is a 400, not an overflow.
- The desk hands the withdrawal form its truck list only once it has been read.
- Deferred (minor): the manager's earlier-counts list is per pass while the lock is per plate; "Try N of 3,
  recount" also shows on a count for a truck nothing was booked for; each refused one-step release leaves
  another pass inside; several held dispatch notes read "Withdrawal DN-1, DN-2 has not been dispatched".
- A plate with no letter or digit in it (`--`) is refused at the gate (`VehicleNumber`): it normalizes to nothing, so it could never match a load or count its tries (found by the PR's Codex review).
